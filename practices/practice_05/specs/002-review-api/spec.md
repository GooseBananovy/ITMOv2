# Feature Specification: HTTP API ревью диффа

**Feature Branch**: `002-review-api`

**Created**: 2026-10-22

**Status**: Draft

**Input**: User description: "Ты — команда логики. Фича: локальный HTTP API ревью диффа поверх review_diff из app/review.py для review-mini. Опиши данные и алгоритм обработки запроса, правила (валидация тела, лимиты, отображение результатов review_diff в ответ), API (метод, путь, формат запроса и ответа, HTTP-коды, ошибки), запуск сервера (адрес, порт, режим с подставной моделью для демо без Ollama). Страницу делает другая команда. Не проектируй интерфейс."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Успешное ревью диффа через HTTP (Priority: P1)

Клиент (страница другой команды, скрипт, curl) отправляет HTTP-запрос с
текстом диффа на локальный сервис и получает текст ревью и статистику
диффа без прямого вызова Python-кода.

**Why this priority**: это основной сценарий использования фичи — без него
API не нужен.

**Independent Test**: запустить сервер в демо-режиме (без Ollama), отправить
запрос с корректным диффом, получить `status: "ok"` с текстом ревью и
`stats`.

**Acceptance Scenarios**:

1. **Given** сервер запущен, диффу меньше лимита и он непустой, **When**
   клиент отправляет запрос ревью с этим диффом, **Then** клиент получает
   успешный ответ с текстом ревью и статистикой диффа.
2. **Given** сервер работает в демо-режиме с подставной моделью, **When**
   клиент отправляет корректный дифф, **Then** клиент получает успешный
   ответ без обращения к настоящей Ollama.

---

### User Story 2 - Понятный отказ при невалидном дифф (Priority: P1)

Клиент присылает пустой, слишком большой или некорректно оформленный
запрос и получает понятный отказ с кодом причины вместо обрыва соединения
или неописанной ошибки.

**Why this priority**: без предсказуемых кодов отказа клиент-страница не
сможет показать пользователю причину и будет вынуждена угадывать.

**Independent Test**: отправить запрос с пустым диффом и отдельно запрос с
диффом больше лимита байт — оба должны вернуть отказ с соответствующим
кодом, модель при этом не вызывается.

**Acceptance Scenarios**:

1. **Given** сервер запущен, **When** клиент отправляет дифф, состоящий
   только из пробелов, **Then** клиент получает отказ с кодом `empty_diff`
   без обращения к модели.
2. **Given** сервер запущен, **When** клиент отправляет дифф длиннее
   лимита байт, **Then** клиент получает отказ с кодом `diff_too_large`
   без обращения к модели.
3. **Given** сервер запущен, **When** клиент отправляет тело запроса, не
   являющееся корректным JSON, или JSON без поля `diff`-строки, **Then**
   клиент получает отказ с кодом ошибки запроса, не доходящий до
   `review_diff`.

---

### User Story 3 - Понятная ошибка при сбое модели (Priority: P2)

Клиент присылает корректный дифф, но модель не отвечает (таймаут,
недоступность, HTTP-ошибка, неожидаемый формат ответа) — клиент получает
структурированную ошибку с кодом причины и статистикой диффа, а не обрыв
соединения или трассировку.

**Why this priority**: это прямое следствие фичи B контракта `review_diff`
— API не должен терять эту информацию при переносе в HTTP-слой.

**Independent Test**: подставить на месте клиента модели объект, который
имитирует каждый из четырёх отказов зависимости, и убедиться, что HTTP-ответ
содержит соответствующий код, сообщение и `stats`.

**Acceptance Scenarios**:

1. **Given** дифф валиден, **When** модель не отвечает дольше отведённого
   времени ожидания, **Then** клиент получает ошибку с кодом
   `model_timeout`, сообщением и статистикой диффа.
2. **Given** дифф валиден, **When** соединение с моделью не устанавливается,
   **Then** клиент получает ошибку с кодом `model_unavailable`.
3. **Given** дифф валиден, **When** модель отвечает HTTP-ошибкой, **Then**
   клиент получает ошибку с кодом `model_http_error`.
4. **Given** дифф валиден, **When** ответ модели не содержит ожидаемых
   полей, **Then** клиент получает ошибку с кодом `model_bad_response`.

---

### User Story 4 - Демонстрация без запущенной Ollama (Priority: P2)

Человек, проверяющий сервис (например, на защите практики), запускает
сервер в режиме с подставной моделью и показывает полный цикл запрос-ответ
без необходимости поднимать настоящую Ollama.

**Why this priority**: контракт требует демо-режим отдельно от тестов —
это сценарий живой демонстрации, а не автоматической проверки.

**Independent Test**: запустить сервер с включённым демо-режимом при
выключенной или недоступной Ollama, отправить корректный дифф и получить
успешный ответ с фиксированным демонстрационным текстом ревью.

**Acceptance Scenarios**:

1. **Given** Ollama не запущена, **When** сервер стартует в демо-режиме и
   получает корректный дифф, **Then** клиент получает `status: "ok"` с
   демонстрационным текстом ревью, без попытки сетевого соединения с
   Ollama.
2. **Given** демо-режим включён, **When** клиент отправляет невалидный или
   приводящий к отказу вход (пустой дифф, слишком большой дифф), **Then**
   поведение отказа идентично режиму с настоящей моделью — демо-режим
   подменяет только обращение к модели, а не валидацию входа.

### Edge Cases

- Тело запроса — синтаксически некорректный JSON (например, обрыв кавычки).
- JSON-тело без поля `diff`, либо `diff` не строка (число, `null`, массив).
- JSON-тело с дополнительными незнакомыми полями помимо `diff`.
- Заявленный или фактический размер тела запроса намного больше лимита
  диффа — тело не должно полностью буферизироваться перед отказом.
- Дифф ровно на границе `MAX_DIFF_BYTES`.
- Дифф, где многобайтовые символы UTF-8 делают подсчёт по байтам и по
  символам разным.
- Запрос с методом, отличным от предусмотренного (например, `GET` на путь
  ревью).
- Запрос на путь, который сервис не обслуживает.
- Несколько запросов одновременно (сервис не должен блокироваться на одном
  медленном запросе к модели так, чтобы остальные не могли даже
  подключиться).
- Демо-режим включён, но Ollama на самом деле доступна — демо-режим не
  должен внезапно отключаться и обращаться к ней.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST предоставлять один HTTP-эндпоинт для отправки
  диффа на ревью, принимающий тело запроса в формате JSON с единственным
  обязательным полем `diff` (строка — текст диффа).
- **FR-002**: Система MUST вызывать существующую функцию `review_diff` без
  изменения её сигнатуры и поведения и возвращать клиенту ровно тот словарь,
  который она вернула (статус, код, сообщение, статистика — без добавления
  или удаления полей на уровне HTTP).
- **FR-003**: Система MUST отображать поле `status` ответа `review_diff` на
  HTTP-код: `"ok"` → 200, `"rejected"` → 400, `"error"` → 502.
- **FR-004**: Система MUST отвергать запрос с кодом ошибки запроса (отдельным
  от кодов `review_diff`) и HTTP-кодом 400, если тело запроса не является
  корректным JSON, либо JSON не содержит поля `diff`, либо `diff` не
  строка — не вызывая при этом `review_diff` и не обращаясь к модели.
- **FR-005**: Система MUST отвергать запрос с HTTP-кодом 400 и отдельным
  кодом ошибки, если заявленный или фактический размер тела запроса
  превышает общий предел размера тела запроса, не дожидаясь полной загрузки
  тела в память. Этот предел — отдельная техническая величина, большая
  `MAX_DIFF_BYTES` с запасом на JSON-обёртку, а не замена бизнес-правилу
  `diff_too_large` из контракта `review_diff`.
- **FR-006**: Система MUST отвечать HTTP-кодом 405 и телом с кодом ошибки на
  запрос к эндпоинту ревью методом, отличным от предусмотренного.
- **FR-007**: Система MUST отвечать HTTP-кодом 404 на запрос к пути, который
  не обслуживается сервисом.
- **FR-008**: Любой ответ сервиса (успех, отказ, ошибка запроса, ошибка
  зависимости модели, 404, 405) MUST быть корректным JSON с
  `Content-Type: application/json` и MUST NOT содержать текст трассировки
  исключения Python.
- **FR-009**: Сервис MUST принимать подключения только на адресе loopback
  (`127.0.0.1`) и не слушать на других адресах или интерфейсах.
- **FR-010**: Сервис MUST поддерживать режим запуска с подставной моделью
  («демо-режим»), включаемый конфигурацией запуска, в котором обращение к
  реальной Ollama не происходит, а вместо него подставляется встроенный
  объект-клиент с фиксированным текстом ревью.
- **FR-011**: В демо-режиме правила валидации входа и классификации ошибок
  зависимости (коды `empty_diff`, `diff_too_large`) MUST работать так же, как
  и вне демо-режима — демо-режим подменяет только сам вызов модели, но не
  обходит проверки `review_diff`.
- **FR-012**: Сервис MUST обслуживать несколько запросов, поступивших
  одновременно, не блокируя обработку новых подключений на время, пока один
  запрос ожидает ответа модели (до `REVIEW_TIMEOUT_SECONDS`).
- **FR-013**: Запуск сервера MUST позволять задать номер порта через
  конфигурацию запуска (например, переменную окружения) отдельно от адреса,
  который остаётся фиксированным (`127.0.0.1`, см. FR-009).

### Key Entities

- **Запрос ревью**: JSON-объект с единственным полем `diff` — строка,
  полный текст диффа, который нужно проверить.
- **Ответ ревью**: JSON-объект, по составу полностью совпадающий со
  словарём, который возвращает `review_diff` (см. `docs/requirements.md`):
  варианты `status: "ok"` (поля `review`, `stats`), `status: "rejected"`
  (поля `code`, `message`, без `stats`), `status: "error"` (поля `code`,
  `message`, `stats`).
- **Ошибка запроса**: отдельная от `review_diff` категория отказа HTTP-слоя
  — некорректный JSON, отсутствующее или нестроковое поле `diff`,
  превышение предела размера тела запроса. Имеет собственные коды, не
  входящие в состав кодов `review_diff` (`empty_diff`, `diff_too_large`,
  `model_timeout`, `model_unavailable`, `model_http_error`,
  `model_bad_response`), и HTTP-код 400.
- **Конфигурация запуска сервера**: порт прослушивания и признак
  демо-режима (вкл/выкл); адрес прослушивания фиксирован и не входит в
  конфигурацию.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Клиент получает результат ревью корректного диффа одним
  HTTP-запросом без необходимости запускать или импортировать Python-код
  сервиса напрямую.
- **SC-002**: 100% запросов с пустым, пробельным или превышающим лимит
  диффом получают отказ с понятным кодом причины и не приводят к обращению
  к модели — проверяется подстановкой клиента модели, который падает при
  вызове.
- **SC-003**: 100% запросов, приводящих к любому из четырёх отказов
  зависимости модели (таймаут, недоступность, HTTP-ошибка, плохой ответ),
  получают структурированный ответ с кодом и статистикой диффа, а не обрыв
  соединения или код 500 без объяснения.
- **SC-004**: В демо-режиме при полностью недоступной или отсутствующей
  Ollama корректный дифф получает успешный ответ в 100% демонстрационных
  запусков.
- **SC-005**: Попытка подключения к сервису с любого адреса, отличного от
  loopback, не находит открытого порта — сервис не становится доступным
  извне машины, на которой он запущен.
- **SC-006**: Одновременная отправка нескольких запросов не приводит к
  тому, что более ранний медленный запрос блокирует приём и завершение
  независимых от него более поздних запросов.

## Assumptions

- Путь эндпоинта, конкретные тексты кодов ошибки запроса (например,
  `invalid_request`, `request_too_large`, `method_not_allowed`) и точные
  значения предела размера тела запроса и порта по умолчанию — детали
  реализации логики, которые эта спецификация фиксирует как подлежащие
  согласованию с контрактом `specs/contract/review-api.md` (Принцип V
  конституции) перед тем, как команда страницы начинает от них зависеть; в
  рамках этой фичи выбираются разумные значения по умолчанию, а не остаются
  открытым вопросом, требующим уточнения у пользователя.
- Предел размера тела запроса устанавливается заметно больше
  `MAX_DIFF_BYTES` (8192 байт), чтобы корректное JSON-тело с диффом на
  границе лимита не отклонялось как «тело запроса слишком велико» из-за
  накладных расходов на JSON-обёртку и экранирование.
- Демо-режим включается явной настройкой запуска (например, переменной
  окружения), а не определяется автоматически по недоступности Ollama —
  это осознанное решение человека, запускающего сервис для демонстрации,
  а не поведение по умолчанию в бою.
- Сервис — однопроцессный, без аутентификации и без TLS, в соответствии с
  тем, что он учебный и однопользовательский (см. конституцию, Принцип VI
  и его rationale).
- `subscribe` из `app/subscribe.py` не затрагивается этой фичей: HTTP API
  в рамках этой спецификации охватывает только ревью диффа.
- Формат и состав полей JSON-ответа для `status: "ok"/"rejected"/"error"`
  не отходит от контракта `docs/requirements.md`: HTTP-слой — это
  прозрачная обёртка над `review_diff`, а не отдельный переформатированный
  контракт.

## Допущения о клиенте — на согласование

Эти пункты описывают, чего команда логики ожидает от клиента (страницы),
но не проектирует интерфейс и не определяет его за другую команду. Нужно
согласовать до того, как страница начинает полагаться на API.

- Клиент отправляет один JSON-объект с полем `diff` (строка, весь текст
  диффа целиком) на один эндпоинт ревью методом из FR-001 — без разбиения
  диффа на части и без multipart/form-data или загрузки файла.
- На один запрос клиент ожидает ровно один ответ целиком (без потоковой
  передачи токенов ответа модели по мере генерации).
- Клиент сам определяет, что показать пользователю, разбирая поля `status`
  и `code` ответа; поле `message` — готовый к показу текст на русском
  языке, формировать свой текст по `code` клиенту не обязательно.
- Клиент учитывает, что HTTP-код 400 может означать как отказ валидации
  диффа (`empty_diff`, `diff_too_large` из контракта `review_diff`), так и
  отдельную ошибку самого запроса (например, некорректный JSON) — коды
  этих двух категорий не совпадают, и клиент не должен считать их
  взаимозаменяемыми.
- При HTTP-коде 502 (ошибка зависимости модели) клиент не повторяет запрос
  автоматически без участия пользователя — повтор, если он нужен, это
  решение и действие на стороне страницы, а не ожидаемое по умолчанию
  поведение сервиса.
- Таймаут ожидания ответа на стороне клиента должен быть больше
  `REVIEW_TIMEOUT_SECONDS` (30 секунд, контракт `review_diff`) плюс сетевой
  запас, чтобы клиент не обрывал соединение раньше, чем сервис успевает
  вернуть `model_timeout`.
- Лимит размера диффа (`MAX_DIFF_BYTES`, 8192 байт в UTF-8) известен
  клиенту заранее из общего контракта; сервис проверяет лимит в любом
  случае, но клиент может (не обязан) предупреждать пользователя до
  отправки.
- В демо-режиме клиенту не нужно ничего менять в своей логике вызова: ответ
  приходит в том же формате, что и с настоящей моделью — отличается только
  содержимое `review`.
- Клиент не ожидает от сервиса сессий, аутентификации, cookie или
  состояния между запросами: каждый запрос ревью самодостаточен.
