Собственный MCP: ошибочный вход и успешный сценарий. 3 октября 2026,
объединённое состояние после мержа фичи B (18 тестов).

=== Вызов агентом (дословно из сессии) ===

  ⚙ review-mini_review_diff {"diff":""}

  Передал: diff = пустая строка ""
  Вернул инструмент:
  {"status":"rejected","code":"empty_diff",
   "message":"дифф пустой или состоит только из пробелов"}

Успешный вызов агентом с нормальным диффом - в evidence/mcp-review-mini.txt.

=== Все четыре случая настоящим MCP-клиентом (fastmcp.Client) ===

[пустая строка]
  -> {'status': 'rejected', 'code': 'empty_diff',
      'message': 'дифф пустой или состоит только из пробелов'}

[5000 символов "ы" = 10000 байт]
  -> {'status': 'rejected', 'code': 'diff_too_large',
      'message': 'дифф больше 8192 байт'}

[число 123 вместо строки]
  -> ToolError: 1 validation error for call[review_diff]
     diff
       Input should be a valid string [type=string_type, input_value=123,
       input_type=int]
     (в логе сервера: WARNING Invalid arguments for tool 'review_diff':
      {'error_count': 1, 'error_types': ['string_type']})

[нормальный дифф "-x = 1 / +x = 2"]
  -> {'status': 'ok', 'review': 'Изменение значения переменной `x` с 1 на 2,
      что может привести к непредвиденному поведению программы.'}

Три разных уровня обработки, и ни на одном наружу не уходит трейсбек:
1. нарушение контракта сервиса - код rejected от самого сервиса;
2. нарушение схемы инструмента - ToolError от слоя MCP, до сервиса не доходит;
3. сбой зависимости - код error от фичи B (проверяется тестами, здесь не
   воспроизводится, чтобы не останавливать Ollama).

Плюс в mcp/review_mcp.py стоит страховка: любое непойманное исключение сервиса
превращается в {"status": "error", "code": "service_exception"}, чтобы агент
никогда не получил стектрейс вместо ответа.
