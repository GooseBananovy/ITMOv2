# Как писать тесты в review-mini

## Через публичный интерфейс

Тест вызывает `review_diff` или `subscribe`. Внутренние помощники могут
переименоваться без предупреждения, контракт — нет.

## Сеть в тестах не используется

Клиент модели передаётся параметром. Два рабочих приёма:

**Запоминающий клиент** — когда нужно проверить, что именно ушло в модель:

```python
class FakeClient:
    def __init__(self, answer="замечаний нет"):
        self.answer = answer
        self.calls = []

    def complete(self, system, user):
        self.calls.append((system, user))
        return self.answer
```

**Падающий клиент** — когда нужно доказать, что модель не вызывалась:

```python
class ExplodingClient:
    def complete(self, system, user):
        raise AssertionError("модель не должна вызываться при отказе")
```

Второй приём важнее первого. Проверять отказ по времени ответа нельзя: быстрый
ответ не доказывает, что вызова не было.

## Клиент, который имитирует сбой зависимости

Для фичи B нужны клиенты, поднимающие те же исключения, что настоящий
`urllib`: `socket.timeout`, `urllib.error.URLError`, `urllib.error.HTTPError`.
Исключение поднимается из `complete`, а проверяется возвращённый код ответа, а
не текст сообщения — текст сообщения для человека и может меняться.

## Имена

`test_<что проверяем>_<при каких условиях>`. Один тест — одно утверждение о
поведении. Если в тесте два `assert` про разные вещи, это два теста.
